PHASE 3 — RAG PIPELINE & INGESTION WORKER
Estimated Duration: 7-10 Days
--------------------------------------------------------------------------------

GOALS
  Implement the full document ingestion pipeline and semantic search. By the end
  of this phase the assistant can ingest a repository or document and retrieve
  relevant chunks to answer questions.

INGESTION PIPELINE SEQUENCE
  1. Source Input      Repository URL or ZIP upload or document upload
  2. Clone / Extract   Git clone into repository-cache volume, or unzip archive
  3. File Filtering    Include .cs .js .ts .tsx .json .xml .yml .yaml .md
                       .sql .html .css .scss .txt
  4. Chunking          Split files into overlapping chunks (512 tokens, 64 overlap)
  5. Embedding         Call Ollama nomic-embed-text per chunk, batch for throughput
  6. Upsert to Qdrant  Store vector + metadata — skip unchanged chunks (hash check)
  7. Update Metadata   Record indexing status, file count, timestamp in PostgreSQL

QDRANT COLLECTIONS
  code-embeddings        Source code chunks
                         Metadata: repo, branch, file path, language, chunk index
  doc-embeddings         Documentation and PDF chunks
                         Metadata: source, title, doc type, page
  instruction-embeddings Coding standards and rules
                         Metadata: rule set name, category, priority

SEARCH MODES
  - Semantic search    Cosine similarity on embedding vectors
  - Hybrid search      Combine vector score with BM25 keyword score
  - Metadata filter    Filter by repo name, language, document type, branch

INCREMENTAL RE-INDEXING
  - SHA-256 hash of each file stored in PostgreSQL
  - On re-index, only files with changed hashes are re-embedded
  - Deleted files are removed from Qdrant and the hash table

SUPPORTED SOURCE TYPES
  GitHub / GitLab / Azure DevOps   Clone via HTTPS with optional PAT for private repos
  ZIP Upload                        Multipart upload — extracted to repository-cache volume
  PDF                               Extracted with PdfPig — chunk by page
  Markdown / TXT / DOCX             Plain text extraction — chunk by paragraph
  Instruction Files (.md)           Stored in instruction-embeddings with priority metadata

NEW API ENDPOINTS
  POST   /api/repositories          Register a repo URL for indexing
  POST   /api/repositories/upload   Upload a ZIP for indexing
  GET    /api/repositories          List all registered repositories and their status
  DELETE /api/repositories/{id}     Remove repository and its vectors
  POST   /api/documents             Upload PDF / MD / TXT / DOCX for indexing
  POST   /api/instructions          Upload coding standards / instruction files
  GET    /api/search                Direct semantic search — query params: q, collection

MILESTONE VERIFICATION
  [ ] POST /api/repositories indexes a public GitHub repo end-to-end
  [ ] Qdrant dashboard shows vectors in code-embeddings collection
  [ ] GET /api/search?q=dependency+injection returns relevant code chunks
  [ ] Re-indexing an unchanged repo skips all files (hash match)
  [ ] PDF upload stores chunks in doc-embeddings collection
  [ ] Instruction file upload stores rules in instruction-embeddings collection

PHASE 4 — AGENT INTELLIGENCE & STREAMING
Estimated Duration: 5-7 Days
--------------------------------------------------------------------------------

GOALS
  Activate the agent stubs from Phase 2 with real logic. Wire Qdrant retrieval
  into the agent pipeline and connect Ollama for generation. Enable true token
  streaming. MCP tool integration is deferred to Phase 8.

ORCHESTRATOR AGENT — FULL IMPLEMENTATION
  - Analyse incoming user message to classify intent
  - Intent categories: code-generation, code-explanation, code-review,
    unit-test, documentation, repository-question, general-question
  - Build agent execution plan based on intent
  - Invoke InstructionAgent first — always retrieve active coding standards
  - Invoke RepositoryAgent if question involves repository context
  - Pass assembled context to CodingAgent for generation
  - Merge and return final response

REPOSITORY AGENT — FULL IMPLEMENTATION
  - Receive query + optional repo filter from Orchestrator
  - Embed query using nomic-embed-text via Ollama
  - Semantic search against code-embeddings collection in Qdrant
  - Apply metadata filters: repository name, branch, language
  - Return top-k chunks with file path, language, and similarity score

INSTRUCTION AGENT — FULL IMPLEMENTATION
  - Always invoked before code generation
  - Retrieve all active instruction files from instruction-embeddings
  - Filter by relevance to current task (e.g. .NET standards for C# tasks)
  - Format rules as a structured system prompt prefix
  - Include forbidden patterns as explicit negative instructions to the model

CODING AGENT — FULL IMPLEMENTATION
  - Receive: user message + retrieved code context + instruction rules
  - Build final prompt: system (instructions) + context (RAG chunks) + user message
  - Call Ollama qwen3-coder:30b with streaming enabled
  - Stream response tokens back through API to client
  - Support all task types: generate, refactor, explain, review, test, document

PROMPT TEMPLATES
  - Templates stored in PostgreSQL prompt_templates table
  - Parameterised placeholders: {instructions}, {context_chunks},
    {user_message}, {language}
  - Separate templates per task type — admin editable via API

MILESTONE VERIFICATION
  [ ] POST /api/chat with a coding question returns real Ollama response
  [ ] Response includes code context retrieved from Qdrant
  [ ] Response adheres to uploaded coding standards
  [ ] Streaming works — tokens appear progressively in client
  [ ] Forbidden patterns (lazy loading, SQL in controllers) not generated

PHASE 6 — ENTERPRISE HARDENING & OBSERVABILITY
Estimated Duration: 5-7 Days
--------------------------------------------------------------------------------

GOALS
  Harden the system for production use. Add comprehensive audit logging,
  structured observability, input validation, secure file handling, and
  backup/restore procedures.

SECURITY
  - Input validation on all API endpoints via FluentValidation pipeline
  - File upload restrictions: allowed extensions, max size, MIME type check
  - Repository URL allowlist / blocklist for enterprise git host control
  - Secrets management: all credentials in environment variables only
  - Audit log table: every API call, user identity, timestamp, action, IP
  - Rate limiting on POST endpoints to prevent abuse

OBSERVABILITY
  Structured Logging    Serilog JSON to stdout — ingest with ELK, Seq, or Loki
  Health Checks         GET /health/ready checks all downstream services
  Metrics               OpenTelemetry counters: requests/sec, embedding latency,
                        agent execution time
  Distributed Tracing   Trace ID threaded through API → Agent → Qdrant → Ollama
  Job Monitoring        Ingestion job status in PostgreSQL via GET /api/jobs

BACKUP & RESTORE
  PostgreSQL     pg_dump to backup volume — schedule via cron or external scheduler
  Qdrant         Qdrant snapshot API — store snapshots in backup volume
  Ollama Models  Volume backup — models can be re-pulled if lost
  Open WebUI     Volume backup — preserves users, chat history, settings
  Restore        pg_restore for Postgres; Qdrant restore snapshot API

CONFIGURATION MANAGEMENT
  - Feature flags in PostgreSQL feature_flags table
  - Admin API endpoints for prompt templates, feature flags, model config
  - All tuneable values (chunk size, overlap, top-k, temperature) in
    appsettings.json
  - Environment-specific overrides via Docker Compose environment sections

RETRY & RESILIENCE
  - Polly retry with exponential backoff on Ollama and Qdrant calls
  - Circuit breaker on embedding calls — fail fast if Ollama is overloaded
  - Ingestion job failure recovery — resume from last successful chunk

DOCUMENTATION DELIVERABLES
  - Deployment Guide — docker compose commands, environment variable reference
  - Local Development Guide — running API outside Docker for hot reload
  - Backup and Restore Guide — step-by-step with all commands
  - Admin Guide — managing repositories, instructions, prompt templates

PHASE 7 — CUSTOM VS CODE EXTENSION
Estimated Duration: 5-7 Days
--------------------------------------------------------------------------------

GOALS
  Build a full-featured custom VS Code extension that integrates the AI coding
  assistant directly into the editor with conversation management, file context,
  direct file editing, plan review, and visual diff approval.

EXTENSION FEATURES

  Chat & Conversation
  - Chat sidebar (WebviewView) — streaming responses token by token via SSE
  - Conversation history UI — list of past conversations in sidebar panel
  - Resume previous conversations — click any conversation to continue it
  - New conversation shortcut — Ctrl+Shift+N starts a fresh conversation
  - Conversation stored in VS Code globalState (persists across sessions)

  Context Awareness
  - Selected code context — active editor selection auto-attached to messages
  - File uploads — attach any workspace file to a message via @ mention or button
  - Context panel — shows exactly what files/code will be sent with the message
  - Active file context — current open file always available as @currentFile

  Code Editing
  - Direct file editing — AI can propose edits to workspace files
  - Plan review before execution — AI describes changes as a plan; user approves
  - Auto-accept toggle — skip manual approval for low-risk changes
  - Visual change review — diff view (before/after) before applying any edit
  - Apply/Reject buttons per change block

  Code Actions (right-click menu on selected code)
  - Review Code, Explain Code, Generate Tests, Document Code, Refactor Code

  Model & Config
  - Model switcher — toggle assistant-14b / assistant-30b from status bar
  - Configurable API base URL via VS Code settings

      historyPanel.ts       — WebviewViewProvider: conversation history list

TOOL-CALLING SUPPORT (GitHub Copilot agent file writing)
  Problem: Copilot's createFile/editFiles tools only trigger when the LLM response
  contains tool_calls JSON — plain text responses are ignored by the tool pipeline.

  Solution: OpenAI function-calling protocol added to /v1/chat/completions:
    1. Copilot sends request with tools[] array (createFile, editFiles, etc.)
    2. ToolCallService parses the tools, builds a tool-aware prompt, calls the LLM
    3. LLM response is parsed for ### File: blocks (our structured edit format)
    4. Each file block is converted to a tool_call JSON object in the response
    5. Copilot receives tool_calls and executes createFile/editFiles in the workspace
    6. Copilot sends tool results back; next turn returns a plain assistant message

  NEW FILES
    AssistantApi.Application/Services/ToolCallService.cs
      — detects tools[] in request, builds tool-aware system prompt
      — parses LLM text response for ### File: blocks
      — converts blocks to OpenAI tool_call format
    AssistantApi.Application/DTOs/ToolCallDtos.cs
      — OpenAiTool, OpenAiToolCall, OpenAiToolChoice, OpenAiToolResult DTOs
      — updated OpenAiChatRequest with Tools and ToolChoice fields
      — updated OpenAiChatResponse/Choice with ToolCalls field

  FLOW
    Request has tools[]  →  ToolCallService.HandleAsync()
                               → builds tool-aware prompt (list available tools)
                               → calls ChatService for LLM response
                               → parses ### File: blocks from response
                               → returns finish_reason="tool_calls" + tool_calls[]
    No tools[]           →  normal ChatService.HandleAsync() (unchanged)

    Tool result turn     →  tool results merged into conversation context
                               → LLM called again for final confirmation message
                               → returns finish_reason="stop"

PHASE 8 — MCP TOOL INTEGRATION
Estimated Duration: 3-5 Days
--------------------------------------------------------------------------------

GOALS
  Extend the agent pipeline with MCP tool servers for direct filesystem and Git
  inspection. This phase is optional — the full RAG pipeline works without it.
  MCP adds exact file lookup and live Git inspection on top of semantic search.

MCP TOOL INTEGRATION
  Filesystem MCP    Read files directly from repository-cache volume
  Git MCP           Run git log, git diff, git blame on cloned repositories
  PostgreSQL MCP    Query metadata DB for repo registration and indexing history
  Docker MCP        Query container health, restart failing services

PREREQUISITES
  dotnet add AssistantApi.Application/AssistantApi.Application.csproj \
    package ModelContextProtocol

DOCKER COMPOSE ADDITIONS
  Add MCP server service definitions to docker-compose.yml, then:
  docker compose up -d
  docker compose ps | grep mcp

USE CASES ENABLED BY MCP
  - "Show me the last 5 commits to UserService.cs" — Git MCP
  - "What changed in this file since last week?" — Git MCP diff
  - "Show me the exact current content of Program.cs" — Filesystem MCP
  - "Which repositories are indexed and when?" — PostgreSQL MCP
  - "Is Ollama healthy right now?" — Docker MCP

MILESTONE VERIFICATION
  [ ] MCP Git tool retrieves exact file content on demand
  [ ] git log / git diff / git blame available to agents
  [ ] Filesystem MCP reads files from repository-cache volume
  [ ] Agents prefer MCP exact lookup over RAG when user requests specific file
